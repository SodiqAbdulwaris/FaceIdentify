# Tools 06 Continuous integration (CI)

## 1. What this is and why it exists

**Continuous integration** means a robot runs the project's checks on every pull request, on a clean
machine, so "it works on my computer" is not good enough to merge. GitHub runs the instructions in
`.github/workflows/ci.yml` (**GitHub Actions**). A PR can be merged only when the required checks are
green **on its exact head commit**; push another commit and the checks start again.

## 2. Where it lives

- The workflow: `.github/workflows/ci.yml` (six jobs).
- The server-side rule that makes five of them required: `.github/rulesets/main.json`
  (`required_status_checks`, `strict_required_status_checks_policy: true`, rebase merge only,
  review threads must be resolved, no bypass).
- The local scripts CI reuses: `.githooks/check-branch-name`, `.githooks/commit-msg`.

## 3. How it works

| Job (as named on the PR) | Runs on | What it checks | Required to merge? |
|---|---|---|---|
| **Branch name** | Linux | the PR's branch is `type/kebab-name` (the same script as the `pre-push` hook) | yes |
| **Commit messages** | Linux | every new commit's header is a valid Conventional Commit of at most 72 characters (the same script as the `commit-msg` hook, run over `base..head`) | yes |
| **Static validation (CI-001)** | Linux | `uv sync --locked`, `ruff format --check`, `ruff check`, `mypy` | yes |
| **Backend fast tests (CI-002, CI-003, CI-005)** | **Windows** | `uv run pytest --cov ...` with `HYPOTHESIS_PROFILE=ci`; excludes `e2e`, `ml_eval`, `benchmark`, `hardware`; uploads the coverage report (kept 14 days) | yes |
| **Frontend (CI-001, CI-004)** | Linux | `npm ci`, regenerates the API types and **fails if they differ from the committed ones**, then typecheck, `lint --deny-warnings`, tests, production build | yes |
| **Desktop shell (TST-047)** | **Windows** | builds the web app, then `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`, the Rust tests against the **real Python backend** (`cargo test -- --ignored`), and the end-to-end desktop workflow (`npm run test:e2e`) | not in the ruleset's list |

Why the backend tests run on Windows: the product is Windows-only, and SQLite file locking and the
native USearch wheels behave differently there. Why the static job runs on Linux: it is cheap, and it
catches Windows-only calls that are not guarded by `sys.platform` (see [ruff and mypy](04-ruff-and-mypy.md)).

Two details that explain behaviours you will see:

- `concurrency: cancel-in-progress` cancels an older run of the same branch when you push again.
- The generated-types step is why changing an API route without running `npm run generate:api` turns a
  PR red: the committed `frontend/src/api/openapi.json` and `schema.d.ts` must match the routes (a backend
  test checks the OpenAPI document, CI checks the TypeScript types).

## 4. Try it

**Works with no models. Verified 2026-10-12** (the pieces CI runs, locally on Linux; the Windows jobs and
GitHub itself cannot be run here).

1. Reproduce **Branch name**: `sh .githooks/check-branch-name "$(git branch --show-current)"`. Expected:
   silent, exit 0, for a correctly named branch.
2. Reproduce **Commit messages** over your branch's commits (this is CI's loop, run locally):

   ```bash
   status=0
   for sha in $(git rev-list --no-merges origin/main..HEAD); do
     git log -1 --format=%B "$sha" > /tmp/msg
     sh .githooks/commit-msg /tmp/msg || { echo "  in commit $sha"; status=1; }
   done
   echo "status=$status"
   ```

   Expected: `status=0` when every header is valid; otherwise the hook prints the bad header and the
   commit's SHA.
3. Reproduce **Static validation**: `uv sync --locked && uv run ruff format --check . && uv run ruff check . && uv run mypy`.
   Expected: the three clean messages from [ruff and mypy](04-ruff-and-mypy.md).
4. Reproduce **Frontend**:

   ```bash
   npm ci
   npm run generate:types --workspace frontend
   git status --porcelain -- frontend/src/api          # must print nothing
   npm run typecheck && npm run lint -- --deny-warnings && npm test && npm run build
   ```

   Expected: `openapi-typescript ... src/api/openapi.json -> src/api/schema.d.ts`, an empty `git status`
   line, `193 passed` for the tests and `built in <1s` for the build (verified on Node 22).
5. Reproduce **Backend fast tests**: `HYPOTHESIS_PROFILE=ci uv run pytest --cov --cov-report=term`. On
   Windows this is CI's command; on Linux the Windows-only tests fail (see
   [pytest](03-pytest.md)).
6. **Desktop shell**: `cd desktop/src-tauri && cargo fmt --check && cargo clippy --all-targets -- -D warnings
   && cargo test` needs Rust and, to compile the shell, the Windows build tools (*unverified here*).

## 5. Change it

You change CI by editing `.github/workflows/ci.yml` or the ruleset. Neither is a routine edit: the
ruleset is applied to GitHub with `gh api -X PUT ...` after editing `.github/rulesets/main.json`
(`.agents/CONTEXT.md` has the command), and a workflow change is a `ci:` commit that must itself pass.
The safe habit is the opposite: **do not change CI to make a failing check pass**; fix the code. When a
check you cannot reproduce fails, open the "Details" link on the PR, read the log from the failing
step, and reproduce that exact command locally.

## 6. Break it on purpose

Push a branch whose commit says `wip stuff`. The **Commit messages** job fails with the hook's message and
names the commit. Edit a route's response model and forget `npm run generate:api`: **Frontend** fails at
`Generated API types are up to date` (and the backend test `tests/contracts/test_openapi_contract.py`
fails first, locally). Both are CI doing its job.

## 7. Exercises

1. Which two CI jobs run the same scripts as local git hooks?
2. Why does the frontend job regenerate the types and then check `git status`?
3. Which jobs run on Windows and why?
4. A PR is green but you push a new commit. Is it still mergeable right away?

**Answers**

1. Branch name (`check-branch-name`) and Commit messages (`commit-msg`).
2. If the committed types differ from what the routes generate, the working tree changes and the job
   fails: the front end and back end cannot silently drift apart.
3. Backend fast tests and Desktop shell, because the product is Windows-only and file locking, native
   wheels and the sidecar's process handling differ there.
4. No. Checks are required on the exact head commit, so they must pass again.
