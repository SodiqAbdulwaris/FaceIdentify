# M5 step 1: naming a person

- **Date:** 2026-10-07
- **Milestone / tracker IDs:** M5 step 1 (TST-054, first part)
- **Status:** done for step 1 (naming, renaming, linking); the corrections that follow are step 2
- **Commits:** PR to be recorded when merged

## What changed

- **Revision `0008`** adds the `PERSON_RENAMED` Evidence kind (CONTEXT question 12), with a populated
  upgrade test, a refused downgrade over a populated table, and the printed-SQL check, like `0006`.
- **Use cases** (`backend/app/people/use_cases.py`): `name_identity` creates the Person and links the
  Identity in the caller's one transaction (an empty name, an unknown, inactive or already-named
  identity is refused before anything is created); `rename_person` now also appends one
  `PERSON_RENAMED` Evidence row, carrying the two revisions and no names (it takes a `new_id`).
- **Routes** (`backend/api/routes/people.py`, API section 7): `POST /people` (name plus the identity
  to name: it creates both, never a Person alone), `GET /people`, `GET /people/{id}`,
  `PATCH /people/{id}` (name plus the revision the client saw; a stale one is
  `409 PERSON_REVISION_CONFLICT`), `POST /people/{id}/assign-identity` and `/remove-identity`.
  Identity and occurrence summaries now carry the person they are named as (`person`: id, name,
  revision), so every screen can show a name without more requests.
- **Frontend:** the person screen has a "Name this person" form (and "Rename" once named); the name
  replaces the derived `Person XXXXXX` label on the people list, the person screen and the face boxes
  on a source. The generated API types are regenerated.

## Why

M5 plan step 1. The owner decided (2026-10-07) that naming normally creates and attaches the Person
atomically and that standalone Person creation is not exposed unless the spec requires it.

## Decisions

> **Decision 2026-10-07:** The API spec lists `POST /people`, which could create a Person alone. The
> route is built as the owner's atomic naming: its body requires an `identity_id`, so no Person
> exists without the identity that prompted it. Standalone creation is not exposed; if a screen ever
> needs a Person with no Identity the spec's route can be widened then. (Agent's reading of the
> owner's decision and the spec; flagged for the owner.)

- The rename event records revisions, not names. Evidence is immutable and a name is personal data
  that must stay changeable; the cost is that the old name is not in the history. Flagged for the
  owner: say so if names must be kept in the event.
- Every successful change to a person publishes a `person.updated` event after the commit (best
  effort, like the others); the client treats it as "every name on screen is stale" (people list,
  person pages, faces on sources). A refused request publishes nothing. (Added after the review.)
- `DELETE /people/{id}`, `GET /people/{id}/identities|occurrences|sources|evidence` are not built:
  nothing in the app needs them yet.
