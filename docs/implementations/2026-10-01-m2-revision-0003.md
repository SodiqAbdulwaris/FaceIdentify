## What changed

- **Revision `0003_ann_key_per_space_and_snapshot_triggers`**:
  1. `representations.ann_key` is `UNIQUE(representation_space_id, ann_key)` instead of table-wide
     `UNIQUE(ann_key)` (decision 2026-10-01, issue #48; also CONTEXT's older question 13). The table is recreated
     from a frozen definition, as in `0002`; every row and key is kept. The model changes the same way.
  2. Two triggers on `processing_configuration_snapshots` (issue #51): `BEFORE UPDATE` always aborts, so a
     committed snapshot never changes (not even to the same values); `BEFORE DELETE` aborts while a run references
     the snapshot and allows deleting one no run references.
- The trigger text is written once in `backend/app/processing/models.py`, attached to the table with an
  `after_create` event so `create_all` builds the same triggers, and copied frozen into the revision. The two must
  stay identical.
- `tests/integration/test_migration_0003.py` (13 tests); the shared helpers are now in
  `tests/fixtures/migrations.py` (extracted from the `0002` tests, which import them); `test_migrations.py`
  (new head, and a test that the trigger text matches `create_all`), `test_schema_contract.py` (the expected unique
  index) and `test_memory_models.py` (the old "unique across the table" test) follow the decision.

## Decisions and findings

- **One snapshot per run needed nothing**: `uq_processing_runs_configuration_snapshot_id` was already in `0001`
  (see the dated correction in the ProcessingRun entry), so only the triggers are new for #51.
- **Every index lookup and removal carries the space and the key** (the owner's rule) was already true: each
  USearch index belongs to one space, the coordinator opens it by the operation's space, and
  `resolve_ann_candidates` looks keys up by the pair. Nothing in `backend/` queries `representations` by
  `ann_key` alone. The new constraint is what makes that rule safe.
- **"Verify the resulting uniqueness" cannot fail on an existing database**: the new constraint is weaker than the
  old, so any database valid before is valid after. What is verified: every key survives, the same key is allowed
  in two spaces, a key twice in one space is refused, and keyless (pending or erased) representations may repeat.
  The strategy's PER-10 had said a violating database would be refused; that was impossible and is corrected.
- **The `DELETE` trigger is narrower than "reject deletions"** (decided in PR 53, flagged for the owner): an
  unreferenced snapshot can be deleted so the Source-deletion lifecycle can remove snapshots after their runs.
  The database cannot tell that lifecycle from any other caller, so that rule is the application's.
- **A known limit of the triggers** (found by the review): `INSERT OR REPLACE` deletes and re-inserts, and SQLite
  does not fire delete triggers for that deletion unless `recursive_triggers` is on (it is off). A snapshot a run
  uses is still protected by the `RESTRICT` foreign key; one **no run uses** can be silently rewritten that way.
  Nothing in the application does it (the repository only `INSERT`s, the ORM never emits it), but the guarantee
  "a committed snapshot never changes" has this exception. It is stated in the spec, CONTEXT and the Alembic
  README, pinned by a test, and a third `BEFORE INSERT` trigger that would close it is the optional hardening in
  issue #55 (beyond the two triggers the owner approved).
- **Spec edits:** the edits to persistence 6.2, 6.3 and 13 follow the owner's recorded decision of 2026-10-01 (PR
  53); they change "not yet built" to "built" and add the limit above, and delete no superseded text.
- **Triggers belong to their table**: a later revision that recreates `processing_configuration_snapshots` would
  silently drop them. The Alembic README now says so.
- **Downgrade** restores the table-wide constraint and drops the triggers; it is refused atomically while two
  spaces hold the same key (tested). That is a fact about this revision, not a decision on Q19.
- **A real defect in my first tests**: the factories give *every* run its own snapshot, so my "snapshot no run
  uses" was in fact used and the delete test failed; the helper now looks for a snapshot not referenced by any
  run.
- **A schema-comparison gap**: the existing comparison of the migrated schema with `create_all` ignored trigger
  text, so a mutation changing one side survived. A new test compares it exactly.
