## What changed
- `backend/alembic/versions/0005_abstain_provenance_snapshot_replace.py`, three changes in one revision:
  1. `representations.active_eligible` CHECK: `state != 'ACTIVE' OR (identity_id IS NOT NULL AND ann_key IS NOT NULL)` becomes `state != 'ACTIVE' OR ann_key IS NOT NULL` (an accepted `ABSTAIN` representation is `ACTIVE` with no identity, decision 2026-10-02). Only the identity half goes; an `ACTIVE` row without a key stays refused.
  2. A nullable `runtime_variant_id` foreign key (`RESTRICT`) on `representations` and on `observations`: the variant that actually executed (decision 2026-10-03, issue 88). Existing rows keep NULL.
  3. `trg_processing_configuration_snapshots_no_replace` (issue 55): `BEFORE INSERT ... WHEN EXISTS` a row with the same id, so `INSERT OR REPLACE` (which fires no delete trigger) and a plain duplicate id are both refused.
  Both tables are recreated in batch mode from frozen definitions (as in revisions 0002 and 0003), so every row is kept and the migrated schema equals `create_all`. Downgrade restores the stricter CHECK, drops both columns and the trigger; the downgrade guard refuses it for a populated library, and with the override it is refused atomically while an identity-less `ACTIVE` row exists.
- Models: `Representation.active_eligible`, `Representation.runtime_variant_id`, `Observation.runtime_variant_id` (the last column of each table, so a fresh database and a migrated one list the same columns), and `SNAPSHOT_NO_REPLACE_TRIGGER` (registered like the other two, byte-identical to the revision's copy).
- Tests: `tests/integration/test_migration_0005.py` (12), the head pins (`test_migrations`: head `0005`, three triggers; `test_library_lifecycle`), `test_memory_models` (the CHECK's two halves).
- **Legacy-revision tests.** The factories build rows with the head models, which now have a column that revisions 0001 to 0004 lack, so the populated-database tests of 0002, 0003 and 0004 can no longer insert into an old database directly. `tests/fixtures/migrations.populate_legacy` builds the rows in a scratch database at the head and copies them, column by column (the columns both have), into the old one; two 0003 tests that insert after the upgrade now run at the head and downgrade back to 0003 before the part they are about.
- Docs: Persistence 6.2 and 13 (dated notes), CONTEXT (issue 55 built; the 88 columns built), the tracker, the M3 decisions entry's list of what 0005 requires (now partly built).
