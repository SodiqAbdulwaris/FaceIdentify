- **Status:** done: M4's definition of done ("the complete desktop image workflow passes end to end

- **Commits:** PR (this change): `test(desktop): run the whole workflow, then restart`

## What changed

- `frontend/e2e/workflow.e2e.tsx` (run with `npm run test:e2e`, not part of `npm test`): one test
  that walks the product the way a person does.
  1. A new library: the screen invites the first import. Three images (two identical pictures and
     a different one, real PNG files made by `e2e/png.ts`) are imported through the stand-in
     native picker: "Imported 3 images."
  2. Each is processed; the cards turn "Done" as the real backend works in the background; the
     uncalibrated-policy notice is shown.
  3. People: two, one seen twice ("2 appearances in 2 images") and one once; the person seen twice
     lists both images; opening an image shows the face's box linking to the person.
  4. The application closes and the backend **stops cleanly** (exit code 0, by closing its standard
     input, exactly as the shell does).
  5. A second launch on the same library (a new process, port and token): every image is there and
     "Done", the same two people exist, and importing and processing a **new copy** of the first
     picture makes no third person: it is recognised from the stored memory (three appearances in
     three images).
- What is real: the web app (React, queries, routes, the event client), HTTP and WebSocket over a
  real loopback socket (`e2e/socket.ts` wraps `ws`, because jsdom's `Event` is not the one Node's
  own WebSocket dispatches), the backend started as the shell starts it (`e2e/backend.ts`: token in
  the environment, parent pid, stdin lifeline, one handshake line), the scheduler, executor,
  acceptance, SQLite and the vector index, on files written by the test. What is stood in for: the
  shell's two native calls (where the backend is, and the file picker) and the perception (the
  development profile's fake).
- CI: the `desktop` job runs it after the Rust tests (Windows, with `uv sync` and the built web
  app). `@types/ws` and `ws` are dev dependencies for the test only.
- Verified by hand: `npm run tauri dev` compiles and starts the app, which creates its library
  under the application data folder (removed again afterwards); no interactive window session was
  driven by hand here.
- A leftover from probing the shell by deliberately broken variants (a heartbeat stub that is not
  killed) was found and removed; nothing in the product leaves a process behind (the tests that
  start failing hosts check that they are ended).

## Why

The milestone gate: the workflow has to work as a whole, and keep working after a restart, not only
in its parts.
